# Требования к единому серверу Activ Daily / Premies Portal

## 1. Назначение документа

Документ определяет конфигурацию одного общего production-сервера для текущей кодовой базы Activ Daily / Premies Portal. Расчёт сделан для следующих условий:

- до 500 пользователей портала в день;
- более 200 000 клиентов в реестре;
- одновременная работа пользовательских API, фоновых задач и генерации документов;
- хранение PostgreSQL, Redis, RabbitMQ, Elasticsearch, загруженных файлов и журналов на одном физическом сервере;
- запуск существующего набора сервисов через Docker Compose.

Рекомендуется один физический сервер. Разделение на четыре или более отдельных сервера для текущего состава проекта не требуется.

## 2. Что фактически работает в проекте

Рекомендация основана на коде и конфигурации следующих компонентов.

| Компонент | Фактическая роль | Характер нагрузки |
|---|---|---|
| `premies_portal_front` | React/Vite-интерфейс, собранный в статические файлы и отдаваемый Nginx | Небольшая нагрузка на CPU и RAM после сборки |
| `premies_portal` | Основной Go API: авторизация, пользователи, клиенты, роли, чат, операции, документы и интеграционные маршруты | Постоянная API-нагрузка, обращения к БД, Redis, RabbitMQ, Elasticsearch и внутренним банковским сервисам |
| `daily_tasks` | Планировщик регулярных заданий, синхронизация клиентов, cashback, обработка транзакций и backfill | Основной источник фоновой нагрузки и параллельных сетевых запросов |
| `abs_service` | Go-сервис доступа к данным ABS и клиентским продуктам | Сетевая I/O-нагрузка и разбор объёмных ответов внешних сервисов |
| `applications_portal` | API заявок и WebSocket/RabbitMQ-обновления | Умеренная API-нагрузка, файлы заявок и события |
| `deposits_portal` | API депозитных заявок | Умеренная API-нагрузка |
| `premies_automation` | Python/gRPC-сервис создания DOCX, XLSX, ZIP и обработки загруженных файлов | Кратковременные пики CPU, RAM и дисковой I/O при генерации документов |
| PostgreSQL 15 | Единое основное хранилище сервисов | Наиболее чувствительный к дисковой задержке компонент |
| Redis 7 | Кэш, блокировки и защита от повторной обработки | Небольшой объём данных, но критичен для корректной работы джоб |
| RabbitMQ 3 | Обмен событиями между сервисами и WebSocket-обновления | Небольшая, но постоянная нагрузка |
| Elasticsearch 8.13 | Централизованное хранение журналов основного API и `daily_tasks` | Последовательная запись и рост дискового объёма |

Второй, неиспользуемый frontend-контейнер, оставшийся в общем `docker-compose.yml`, в расчёт не включён и на production-сервере запускаться не должен.

## 3. Почему основная нагрузка создаётся не интерфейсом

### 3.1. Фоновые задачи

В `daily_tasks/internal/jobs/jobs.go` зарегистрировано 16 постоянно работающих заданий:

- 1 задача запускается каждые 10 секунд;
- 5 задач запускаются каждую минуту;
- 1 задача запускается каждые 2 минуты;
- 7 задач запускаются каждые 5 минут;
- 1 задача запускается каждые 10 минут;
- 1 задача запускается каждый час.

Задачи выполняют поиск транзакций, возврат cashback, проверку reversal, обновление типов операций, синхронизацию клиентов и другие обращения к Daily, ABS и processing-сервисам.

В коде также реализован backfill с обработкой временных окон. В отдельных обработчиках используется до 5–10 параллельных workers, а синхронизация клиентского справочника допускает до 12 параллельных подразделений. Поэтому во время backfill фоновая нагрузка может быть заметно выше обычной, даже если в портале находится мало пользователей.

### 3.2. Клиентский реестр

200 000 строк клиентов сами по себе не являются большой нагрузкой для PostgreSQL. Нагрузка возникает из-за периодического обогащения каждой записи данными внешних сервисов, проверок комплайнс, мобильного банка, фильтрации по подразделениям и повторных обновлений.

Для такой схемы важнее быстрый NVMe-диск, корректные индексы и ограничение параллельности, чем отдельный сервер только под клиентский реестр.

### 3.3. Генерация документов

Python/gRPC-сервис содержит обработчики формирования DOCX, XLSX, ZIP, справок, реквизитов и отчётов. Такие операции создают кратковременные пики процессорной нагрузки и активно используют временные файлы и память. Для них нужен запас ресурсов, но отдельный физический сервер при текущей ожидаемой аудитории не требуется.

### 3.4. Журналы

Go-сервисы используют `lumberjack` и уже умеют ротировать файловые журналы. Основной API и `daily_tasks` дополнительно отправляют записи в Elasticsearch, а информационные сообщения также попадают в stdout контейнеров. Следовательно, одна запись может занимать место одновременно в файле, Docker-журнале и Elasticsearch.

Именно журналы, выгрузки и загруженные документы, а не 200 000 записей клиентов, являются главным основанием для большого дискового резерва.

## 4. Рекомендуемая конфигурация одного сервера

Для production рекомендуется один физический сервер следующей конфигурации.

| Ресурс | Требование |
|---|---|
| CPU | 32 физических ядра, не менее 64 потоков, базовая частота от 2,5 ГГц |
| RAM | 256 GB ECC с возможностью расширения до 512 GB |
| Системные диски | 2 × 1,92 TB enterprise NVMe SSD, RAID 1 |
| Диски данных | 4 × 3,84 TB enterprise NVMe SSD, RAID 10; около 7,68 TB полезного объёма |
| Сеть | 2 × 10 GbE с резервированием подключения |
| Питание | 2 резервируемых блока питания |
| ОС | Linux LTS, поддерживаемый службой эксплуатации банка |
| Запуск приложений | Docker Engine и Docker Compose v2 |
| GPU | Не требуется для текущей кодовой базы |

Для NVMe-дисков требуются серверные модели с защитой от потери питания. PostgreSQL, Elasticsearch, каталоги загрузок и журналы должны размещаться на массиве данных, а ОС, Docker Engine и образы контейнеров — на системном RAID 1.

### Почему выбраны 32 ядра

- статический frontend почти не использует CPU;
- Go API экономно используют память и процессор в обычном режиме;
- CPU-запас требуется для одновременной работы 16 джоб, backfill, синхронизации клиентов и генерации документов;
- значительная часть времени интеграционных задач уходит на ожидание ответов Daily, ABS и processing, а не на вычисления;
- 32 физических ядра позволяют оставить ресурсы PostgreSQL и пользовательским API даже во время параллельной фоновой обработки.

### Почему выбраны 256 GB RAM

Ориентировочный рабочий бюджет памяти:

| Группа процессов | Рабочий бюджет RAM |
|---|---:|
| PostgreSQL и его файловый кэш | 64–80 GB |
| Elasticsearch | 16 GB, включая heap 8 GB |
| Redis и RabbitMQ | до 16 GB суммарно |
| Все Go API-сервисы | до 32 GB суммарно |
| `daily_tasks`, включая backfill | до 32 GB |
| Python/gRPC и генерация документов | до 32 GB |
| Nginx frontend | до 2 GB |
| ОС, Docker и свободный резерв | не менее 46 GB |

Такой объём не рассчитан на постоянное заполнение всей памяти. Свободная RAM нужна Linux для файлового кэша и для кратковременных пиков при массовой выгрузке, backfill или генерации документов.

512 GB RAM для текущего кода не является обязательным требованием. Возможность расширения нужна только как запас на последующий рост данных и появление новых тяжёлых сервисов.

### Почему требуется около 7,68 TB полезного диска

Рекомендуемое распределение массива данных:

| Данные | Резерв |
|---|---:|
| PostgreSQL, индексы и запас на обслуживание | до 2,5 TB |
| Elasticsearch и его индексы журналов | до 1,5 TB |
| Загруженные файлы заявок, DOCX/XLSX/ZIP и временные файлы | до 1,5 TB |
| Файловые и Docker-журналы | до 0,5 TB |
| Свободное место для роста и безопасных операций БД | не менее 1,5 TB |

PostgreSQL и Elasticsearch не должны работать на диске, заполненном более чем на 80%. Свободный резерв также нужен для перестроения индексов, миграций и временных файлов.

## 5. Размещение сервисов на одном сервере

Все компоненты продолжают работать отдельными контейнерами в одной Docker Compose-схеме. Разделение выполняется не по физическим серверам, а лимитами ресурсов и отдельными каталогами/volume.

Рекомендуемое базовое распределение CPU:

| Группа | Гарантированный ориентир | Допустимый кратковременный рост |
|---|---:|---:|
| PostgreSQL | 8 ядер | до 12 ядер |
| Основной API и остальные Go API | 8 ядер суммарно | до 16 ядер |
| `daily_tasks` | 6 ядер | до 12 ядер |
| Python/gRPC | 4 ядра | до 8 ядер |
| Elasticsearch, Redis и RabbitMQ | 4 ядра суммарно | до 8 ядер |
| Nginx и системные процессы | 2 ядра | до 4 ядер |

Кратковременные пределы могут пересекаться: они нужны для использования свободных ресурсов, а не для одновременной гарантии максимума каждому контейнеру. Приоритет должен оставаться у PostgreSQL, основного API и Nginx; backfill и генерация больших файлов должны получать оставшиеся ресурсы.

## 6. Обязательные настройки перед переносом нагрузки

### 6.1. Docker Compose

Для всех прикладных контейнеров необходимо задать:

- автоматический перезапуск после сбоя и перезагрузки сервера;
- ограничения RAM и CPU согласно разделу 5;
- проверку работоспособности для основного API, `daily_tasks`, сервисов заявок, депозитов и Python/gRPC;
- ограничение Docker-журналов по размеру и количеству файлов;
- отдельные постоянные volume для PostgreSQL, Elasticsearch и пользовательских файлов.

Текущий compose уже содержит healthcheck для PostgreSQL, Redis, RabbitMQ, Elasticsearch и `abs_service`, но не для всех прикладных сервисов. Это необходимо выровнять до ввода нового сервера.

### 6.2. PostgreSQL

Все Go-сервисы используют GORM и одно общее подключение к PostgreSQL. В текущем коде не найдено явной настройки `SetMaxOpenConns` и `SetMaxIdleConns`. До нагрузки необходимо ограничить пулы каждого сервиса, чтобы несколько контейнеров и параллельные джобы не исчерпали соединения БД.

Также необходимо проверить индексы как минимум для полей, используемых в реестре и операционных выборках:

- код клиента;
- подразделение;
- телефон и ИНН;
- номер счёта и ID карты;
- статус и дата создания;
- идентификаторы транзакций;
- cursor и статус фоновых задач.

### 6.3. Elasticsearch и журналы

В текущем `docker-compose.yml` Elasticsearch ограничен heap 512 MB. Для хранения журналов основного API и `daily_tasks` на общем production-сервере необходимо установить heap 8 GB и общий лимит контейнера 16 GB.

Также необходимо:

- хранить журналы Elasticsearch не более 30 дней либо удалять старые индексы раньше при достижении 70% диска;
- оставить debug-уровень выключенным в production;
- не дублировать подробные тела успешных внешних ответов в info-журналах;
- ограничить stdout-журналы Docker, поскольку файловая ротация Go-приложения не ограничивает собственный журнал Docker.

### 6.4. Фоновые задачи

Код уже содержит Redis-блокировки, сохранение progress/cursor и отмену backfill. На сервере необходимо сохранить следующие эксплуатационные правила:

- обычные задания продолжают работать по расписанию во время backfill;
- для backfill сохраняются существующие ограничения обработчиков: до 5 параллельных workers для переводов и до 10 для карточного cashback;
- массовая синхронизация клиентов запускается с текущим программным ограничением до 12 параллельных подразделений;
- повторный запуск одной и той же джобы не должен создавать параллельный дубликат;
- при недоступности Daily, ABS или processing задача фиксирует ошибку и переходит к следующему циклу, а не создаёт бесконечный поток повторов.

## 7. Резервное копирование при одном сервере

Один сервер является единой точкой отказа, поэтому резервные копии нельзя хранить только на его RAID-массиве. RAID защищает от отказа диска, но не от удаления данных, повреждения БД или отказа всего сервера.

Необходимы:

- ежедневная резервная копия PostgreSQL;
- копирование загруженных документов и файлов заявок;
- хранение копий во внешней системе резервного копирования банка;
- ежемесячная проверка восстановления PostgreSQL и одного набора загруженных файлов;
- резерв конфигурационных файлов и переменных окружения отдельно от исходного кода.

Отдельный сервер приложений для этого не требуется: используется существующая внешняя система хранения резервных копий.

## 8. Что не входит в текущий расчёт

В текущей кодовой базе нет runtime, контейнера, зависимостей и моделей для выполнения нейросетевого инференса. Поэтому GPU и память под него в конфигурацию не включены. После появления конкретного сервиса и выбранной модели его потребление необходимо измерить отдельно; до этого закупка GPU не имеет подтверждения со стороны проекта.

Также в расчёт не включён неиспользуемый второй frontend.

## 9. Итоговое решение

Для текущего проекта и заявленного роста достаточно одного общего сервера:

> **32 физических ядра / 64 потока, 256 GB ECC RAM, 2 × 1,92 TB NVMe RAID 1 для системы, 4 × 3,84 TB NVMe RAID 10 для данных, 2 × 10 GbE, резервируемое питание, Linux LTS, Docker Engine и Docker Compose v2.**

Эта конфигурация обоснована фактическим составом проекта: статический frontend, несколько Go API, 16 плановых джоб с backfill, Python/gRPC-генератор документов, PostgreSQL, Redis, RabbitMQ и Elasticsearch. Основной запас выделен под параллельные фоновые задачи, дисковую I/O PostgreSQL, генерацию файлов и рост журналов.

## 10. Файлы проекта, использованные для анализа

- корневой `docker-compose.yml` — фактический состав контейнеров, зависимости, volume и открытые порты;
- `premies_portal_front/Dockerfile` и `package.json` — сборка React/Vite и выдача через Nginx;
- Dockerfile и `go.mod` сервисов `premies_portal`, `daily_tasks`, `abs_service`, `applications_portal`, `deposits_portal`;
- `daily_tasks/internal/jobs/jobs.go` — перечень и интервалы 16 плановых задач;
- `daily_tasks/internal/jobs/backfill.go` — обработка временных окон, progress и отмена backfill;
- `daily_tasks/internal/jobs/customer_directory.go` — пакетная синхронизация клиентов и ограничение параллельности;
- `daily_tasks/internal/jobs/card_cashback.go` и `client_transfer_backfill.go` — worker-ограничения фоновой обработки;
- `premies_automation/internal/grpc` и proto-файлы — DOCX/XLSX/ZIP и файловые операции;
- `pkg/logger/logger.go` Go-сервисов — файловая ротация и отправка журналов в Elasticsearch;
- `pkg/db/connections.go` Go-сервисов — общая схема подключения к PostgreSQL через GORM.
