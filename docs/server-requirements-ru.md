# Рекомендации по серверной инфраструктуре Activ Daily / Premies Portal

Документ описывает целевую инфраструктуру для стабильной работы внутреннего портала при росте нагрузки до 500 ежедневных пользователей, 200 000+ клиентов, большом количестве фоновых задач, тяжёлых логах и будущих AI-функциях на базе YOLO и локальных Llama/Ollama-подобных моделей.

## Короткий вывод

Главная нагрузка в этой системе — не 500 пользователей в день, а фоновые джобы, синхронизация клиентов, массовые проверки, генерация документов, обращения к внешним сервисам Daily/ABS/processing и объём логов. Поэтому инфраструктуру лучше разделить минимум на четыре зоны:

1. API и frontend gateway.
2. Фоновые jobs/worker-сервисы.
3. База данных и кэш.
4. Логи, мониторинг и AI-инференс.

Если всё держать на одном сервере, система будет работать, но любой backfill, тяжёлая сверка, массовое обновление клиентов или AI-модель смогут “забить” CPU/RAM/диск и повлиять на портал. Для стабильности лучше разделить роли.

## Рекомендуемая production-схема

### 1. Узел API / backend-сервисов

Назначение: пользовательские API, авторизация, операции фронтовика, генератор документов, внутренние REST-сервисы.

Рекомендуемая конфигурация:

- CPU: 16–24 физических/виртуальных ядра.
- RAM: 64–128 GB.
- Disk: NVMe SSD 1–2 TB.
- Network: 10 GbE внутри серверного контура.
- OS: Linux LTS.
- Runtime: Docker/Podman + systemd или Kubernetes, если уже есть компетенция сопровождения.

Примечание: API-сервисы не должны конкурировать с тяжёлыми backfill-джобами и AI-моделями за CPU/RAM.

### 2. Узел фоновых задач / jobs

Назначение: `daily_tasks`, cashback jobs, сверки, backfill, массовые проверки клиентов, обновления статусов, интеграции с Daily/processing.

Рекомендуемая конфигурация:

- CPU: 24–32 ядра.
- RAM: 128 GB.
- Disk: NVMe SSD 2 TB.
- Network: 10 GbE.
- Отдельные очереди для обычных задач и backfill.

Обязательные требования к jobs:

- Каждая задача должна быть идемпотентной: повторный запуск не должен портить данные.
- Backfill должен работать отдельным низкоприоритетным режимом, чтобы не блокировать текущие операции.
- Для каждой задачи нужен cursor/progress: дата/время последнего обработанного окна, статус, количество обработанных записей, последняя ошибка.
- Нужны лимиты параллельности: отдельно для внешних сервисов Daily/ABS/processing, чтобы не положить интеграции.
- Retry только с backoff: например 1 минута → 5 минут → 15 минут.
- Нельзя писать бесконечные error logs без rate-limit, иначе диск забьётся раньше, чем проблема будет замечена.

### 3. Узел базы данных

Назначение: PostgreSQL/основное хранилище портала, клиенты, роли, документы, jobs state, audit.

Рекомендуемая конфигурация:

- CPU: 32 ядра.
- RAM: 256 GB.
- Disk: enterprise NVMe SSD, полезный объём 4–8 TB.
- RAID: RAID 10 или отказоустойчивая storage-схема.
- Backup: ежедневный полный backup + WAL/PITR.
- Network: 10 GbE.

Рекомендации:

- Использовать PgBouncer или другой connection pooler.
- Индексировать поля, по которым идут массовые фильтры: client code, phone, INN, account, cardId, status, CreatedAt, job cursor.
- Большие таблицы логов/истории/транзакций партиционировать по дате.
- Хранить технические логи отдельно от бизнес-таблиц.
- Начальное значение `shared_buffers` для PostgreSQL обычно разумно держать около 25% RAM и дальше тюнить по метрикам.

### 4. Узел логов и мониторинга

Назначение: централизованные логи, метрики, алерты, диагностика зависаний jobs.

Рекомендуемая конфигурация:

- CPU: 8–16 ядер.
- RAM: 64 GB.
- Disk: 4–8 TB, в зависимости от срока хранения логов.
- Stack: Prometheus + Grafana + Loki или ELK/OpenSearch.

Обязательно:

- Включить ротацию Docker-логов. Дефолтный `json-file` без лимитов может быстро заполнить диск.
- Для Docker лучше использовать `local` logging driver или явно задать `max-size` и `max-file`.
- Хранить error logs отдельно от info/debug.
- Debug logs включать только временно.
- Сделать алерты:
  - диск занят больше 75/85/90%;
  - PostgreSQL connections > 80%;
  - job lag больше допустимого окна;
  - рост 5xx ошибок;
  - внешние сервисы Daily/ABS/processing недоступны;
  - RAM/CPU держатся выше 85%;
  - очередь backfill не двигается.

Для Prometheus размер retention-storage желательно ограничивать так, чтобы он не занимал больше 80–85% доступного диска.

### 5. Узел AI-инференса

Назначение: YOLO-модель, локальные Llama/Ollama/vLLM/Triton модели, будущие AI-функции.

Минимальная стартовая конфигурация:

- CPU: 24–32 ядра.
- RAM: 128 GB.
- GPU: 1 × NVIDIA L40S 48 GB.
- Disk: NVMe SSD 2–4 TB.
- Network: 10 GbE.

Комфортная production-конфигурация:

- CPU: 32–48 ядер.
- RAM: 256 GB.
- GPU: 2 × NVIDIA L40S 48 GB или 1 × NVIDIA H100 80/94 GB.
- Disk: NVMe SSD 4 TB.

Если планируется Llama 70B с нормальной скоростью и несколькими одновременными пользователями, лучше сразу закладывать H100/A100-класс или минимум 2 × L40S. Для YOLO и небольших/средних Llama-моделей 1 × L40S — хороший баланс цены и возможностей.

AI-сервис должен быть отделён от основного портала. Даже если модель зависнет или займёт всю GPU-память, портал, jobs и база не должны пострадать.

## Если нужен один большой физический сервер

Это хуже с точки зрения отказоустойчивости, но возможно как первый этап.

Рекомендуемая конфигурация одного сервера:

- CPU: 2 × AMD EPYC / Intel Xeon, суммарно 48–64 ядра.
- RAM: 512 GB.
- Disk:
  - 2 × NVMe 1.92 TB RAID 1 для OS/runtime;
  - 4–8 × NVMe SSD, полезный объём 8–16 TB под DB/logs/files;
  - отдельный backup вне сервера.
- GPU: 1–2 × NVIDIA L40S 48 GB.
- Network: 10 GbE.
- PSU: redundant.
- UPS: обязательно.

Но даже на одном физическом сервере сервисы надо изолировать лимитами CPU/RAM и разнести по отдельным контейнерам/volume.

## Рекомендованный минимум на ближайший рост

Для стабильного запуска без излишней роскоши:

- 1 сервер для API/frontend gateway: 16 CPU, 64 GB RAM, 1 TB NVMe.
- 1 сервер для jobs: 24 CPU, 128 GB RAM, 2 TB NVMe.
- 1 сервер для DB: 32 CPU, 256 GB RAM, 4 TB enterprise NVMe.
- 1 сервер для logs/monitoring: 8 CPU, 64 GB RAM, 4 TB disk.
- 1 сервер для AI: 32 CPU, 128–256 GB RAM, 1 × NVIDIA L40S 48 GB, 2–4 TB NVMe.

## Что обязательно сделать до роста нагрузки

1. Вынести backfill из обычных jobs.
2. Добавить централизованный job-state: статус, cursor, progress, last error, started by, cancelled by.
3. Ограничить параллельность запросов к Daily/ABS/processing.
4. Добавить idempotency keys для задач, которые обновляют транзакции.
5. Настроить ротацию логов.
6. Включить мониторинг PostgreSQL, API latency и job lag.
7. Настроить резервное копирование и регулярно проверять восстановление.
8. Отделить AI-инференс от API и jobs.
9. Для генерации DOCX держать отдельный worker pool, чтобы массовая генерация не блокировала обычные API.
10. Для таблиц клиентов и транзакций проверить индексы и пагинацию, потому что 200 000 клиентов — это уже не режим “загрузить всё на фронт”.

## Источники и технические основания

- NVIDIA L40S: официальная страница указывает 48 GB GDDR6 ECC и позиционирует карту для AI/графики/data center workloads: https://www.nvidia.com/en-us/data-center/l40s/
- NVIDIA H100: официальная страница и product brief описывают H100 как high-end GPU для AI/HPC с вариантами 80/94 GB и поддержкой MIG: https://www.nvidia.com/en-us/data-center/h100/
- Ultralytics YOLO: официальная документация по YOLO-моделям и deployment: https://docs.ultralytics.com/
- Docker logging: официальная документация рекомендует настраивать logging driver и ротацию, потому что дефолтный `json-file` без лимитов может расти бесконтрольно: https://docs.docker.com/engine/logging/configure/
- PostgreSQL resource configuration: официальная документация даёт стартовую рекомендацию около 25% RAM для `shared_buffers`: https://www.postgresql.org/docs/current/runtime-config-resource.html
- Prometheus storage: официальная документация рекомендует ограничивать retention по размеру и не занимать весь диск: https://prometheus.io/docs/prometheus/latest/storage/
- Практические оценки VRAM для Llama 70B зависят от квантизации и runtime; для Q4/production обычно нужно около 50+ GB VRAM, поэтому для стабильной работы лучше планировать L40S 48 GB как минимум для средних моделей, а H100/A100/2×L40S — для 70B и высокой параллельности.
